## 一、用户确认的简历生成规则（2026-08-17，不得回退）

1. **页面使用率**：下限 92%，不排斥占用率高；最终不得超过一页简历。
2. **bullet 组织**：最匹配的经历至少 3 个 bullet；匹配程度较低的至少 2 个 bullet；
   每个 bullet 尾行须 > 行宽 70%，且末尾无句号。
3. **经历充足判定**：在不补充内容的前提下，能从经历仓库挑选与目标岗位匹配的经历，
   按第 2 点组织后即可达到 92% 且不超过一页 → 充足；否则不充足，转入第 4 点。
4. **经历不充足**：harness 主动询问用户是否有其他经历、或继续扩充某条经历，通过追问
   引导补充内容；得到足够内容后，与用户确认是否需要同步保存到经历仓库。
5. **超过一页**：由 Agent 自主删减与目标岗位匹配度较低的经历或 bullet，无需询问用户。
6. **特质补充**：Agent 可主动补充原始经历中没有、但优秀简历应当具备的特质内容；补充
   内容写完后，在对话中明确告知用户"我们帮你写了一些内容，这部分需要你确认一下"，
   经用户确认后视为定稿。

## 七、v44 后分阶段稳定性修复（2026-08-18 用户确认）

### 阶段 1：页面增高与尾行收尾解耦（已完成）

- v44 真实 Electron 基线：投资者关系实习生 JD 用时 242.109 秒，单页、usage 79.8%、
  仍缺 9 行且有 10 条短尾；无 tool error，但 4 次相同进度的 apply 后由通用 governor
  终止。重复证据已被账本拒绝，纯文本计划也已由 Pi follow-up 续跑，因此本轮根因是
  `lineCandidates` 同时要求“恰好多一行 + 新尾行立即合格”的落地窗口过窄。
- `selectLineCandidates` 现只把“真实排版恰好多一行”作为增高阶段的落地资格；同一 bullet
  有多个合格候选时按真实尾行饱满度择优，达到 70% 后保持更短候选。最终 >70% 门槛、
  单页与 92% 均未放宽，达到页面高度后仍进入独立 `batch_tail_repair`。
- 回归将一个只有短尾但能增加一行的候选验证为可落地，同时验证同批更饱满候选被优先选择。
  目标测试 22/22、Node typecheck、659 个源文件行数门禁全部通过。

### 阶段 2：Agent 显式暂停补充素材与恢复闭环（已完成）

- 新增 `pause_resume_for_material`：只有 Agent 判断现有可靠事实不足时才调用，并提交语义原因、
  一个具体追问及可选目标经历；宿主只持久化声明并切换到 `needs_user_decision`，不使用关键词、
  正则或宿主语义评分替 Agent 做决定。暂停后 `apply_resume_content` 为可恢复拒绝，防止后台
  follow-up 继续空转。
- 用户回答后，`add_resume_material` 一次接收多条明确事实，清除暂停并恢复同一 workspace；
  用户补充事实与原经历不可变摘录都可作为 grounded evidence。混合引用仍保留原经历 binding，
  supplemental-only bullet 不再被错误判为“缺少绑定”；同一补充事实只允许消费到一条 bullet，
  避免重复膨胀。
- `generationWorkspaceStatus` 统一复用真实版面/证据可达性判定，机械不可达也能正确进入
  `needs_user_decision`。回归覆盖“暂停 → 阻止写入 → 用户补充 → 恢复 → 写入并通过证据门禁”；
  目标测试 23/23、Node typecheck、660 个源文件行数门禁通过。包含该改动的整套测试为
  530 tests：528 pass、2 平台 skip、0 fail。

### 阶段 3：完整 bullet 多候选批量实测（已完成）

- 删除 `line-clause-normalizer` 及宿主对子句的去重、去前缀、加标点和累积拼接；
  `lineCandidates` 改为每个目标由 Agent 一次提交 1–3 条完整 bullet candidates。语义改写
  全部归 Agent，宿主不再拼装文本。

## 2. 核心数据结构

```ts
// resume-generation-orchestrator.ts
type GenerationPhase =
  | { name: "select" }
  | { name: "write"; pendingBatches: ExperienceBatch[]; repairs: RepairItem[] }
  | { name: "finalize"; round: number }
  | { name: "augment" }
  | { name: "ask_material" };

interface ExperienceBatch {
  experienceId: string;
  tier: "main" | "secondary";
  bulletCount: number;          // 规则 2：main≥3、secondary≥2
  jdRequirementIds: string[];   // 本经历证据命中的 JD 要求
}

interface SelectionProposal {
  jdId: string;
  items: ExperienceBatch[];
}

interface PhaseResult {
  next: GenerationPhase | "done";
  messages: AgentMessage[];     // 本 Phase 的消息（thinking 保留在记录，不进下个 Phase 输入）
}
```

## 3. 关键判定公式

- **P1 充足判定**（规则 3，宿主确定性）：
  `estimatedLines = fixedLines + Σ(bulletCount × 2.5)`（每 bullet 按 2.5 行保守估算）；
  充足 ⟺ `estimatedLines ≥ requiredBulletLinesAtMinimum` 且 `estimatedLines + 页余量 ≤ 总行数`。
  `fixedLines / requiredBulletLinesAtMinimum / charsPerLine` 来自 calibrateTypography（复用现有布局预算）。
- **P1 校验**：experienceId 必须在经历库；tier ∈ {main, secondary}；bulletCount 满足规则 2；
  JD 要求覆盖：模型选择按命中要求数降序，宿主分数（命中要求数 × 权重）与选择明显背离时打回。
- **P3 收尾判定**：`usageRatio ≥ 0.92 且 pageCount === 1` → 达标 → 进 P5；
  `pageCount > 1` → 超页：指令模型自主删减（规则 5），2 轮内仍超页 → 宿主按最低匹配度
  （tier=secondary 优先）提示删减并重 compile（降级：宿主只删 tier 最低且 bullet 最少的条目）；
  `usageRatio < 0.92 且 0.92 − usage ≤ 0.03` → 补长窄通道（改写描述，不需新证据）；
  `usageRatio < 0.92 且差距 > 0.03 且证据耗尽` → P4。
- **P5 确认**：augmented bullet 写入后 `awaitingUserConfirmation` 置位；用户下一条消息命中
  `确认|可以|没问题|ok` 等 → 清除标记定稿；命中否定/删除 → 移除该 bullet 并重 compile；
  其他回复 → 保留待确认状态并再次提示。

## 4. 降级路径（防死锁，不放弃生成）

- P1 模型选择被连续打回 2 次 → 宿主按 JD 覆盖率分数自动生成选择（tier 按分数阈值），
  记录"宿主代选"并继续；
- P2 单批连续 2 轮无新落盘（同结果）→ 跳过该批剩余条目，记录缺口进 P3；
- P3 连续 2 轮 usage 无变化 → 按当前状态收尾：达标进 P5，否则 P4；
- 任一 Phase 单次模型调用超时/出错 → 重试 1 次；仍失败 → 降级/收尾，不抛给用户。
